# 知识库管理技能（列候选 / 评审与晋升 / 核验链接）

> 项目自有文件：位于 `.claude/skills/`，不在 `template-sync.json` 同步清单内，模板同步不覆盖。
> 与场景剧本 `knowledge/scenarios.md` K3 / K4 / K5 同源，是其「执行层」；与剧本冲突时以剧本为准。
> 零依赖设计：不配脚本，全部用会话内 grep / WebFetch 完成；未来量大再评估是否加抽取脚本（需另行登记 §2 例外）。

## 1. 用户说法

- 「列候选」「有什么待评审」「评审清单」「盘点一下知识库」
- 「评审通过 XX」「这条转正」「CASE-xxx 可以转 reviewed」
- 「晋升提名 XX」「PAT-VIS-101 想进母模板」
- 「核验链接」「来源链接还活着吗」「刷新核验」

## 2. 适用场景

- **用**：库存盘点（只读）、单条评审状态变更（candidate → reviewed）、模式回流提名（路由 K3）、来源链接批量核验与核验列刷新。
- **不用**：
  - 收集新来源 / 新观察（走 `.claude/skills/collect-source/`）
  - 上游语料仓更新（走 K2）
  - 已 reviewed 记录的内容修改或降级废弃（单独确认，`deprecated` 留痕）
  - 批量把候选自动升 reviewed（**永远不做**——评审是唯一必须人工的步骤）

## 3. 必读文件

1. `knowledge/README.md` —— 四类记录模型与生命周期口径（candidate / reviewed / core / deprecated）
2. `knowledge/sources.md` —— 来源登记表结构与核验列
3. `knowledge/scenarios.md` —— K3 / K4 / K5 场景剧本
4. `ai/rules-core.md` §2 —— 写入前确认等硬规则
5. 涉及版本留痕时：`ai/project-rules.md` §2.4（单条修正 / 链接核验更新记 PATCH）

## 4. 操作一：列候选（场景 K4）

只读盘点，不改任何文件。

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 全库扫状态标记 | 四类记录都要覆盖，不能漏类 | grep `knowledge/` 下 `candidate`、`待复核`、`提名`、`deprecated`；范围含 `cases/`、`patterns-*.md`、`principles.md`、`sources.md` |
| 2 | 汇总清单 | 让用户能逐条决策 | 表格输出：ID / 类型 / 证据级 / 状态 / 一句话内容 / 挂起事项（如「待第 2 观察来源」） |
| 3 | 给评审建议顺序 | 支撑 Phase1「建立评审节奏」目标 | 最老或最影响消费的排前；仅建议，不替人决定 |

- 输出后停，等用户逐条点名处理；不自动改状态。

## 5. 操作二：评审与晋升

两条路径，动作前都必须有用户明确指令：

**① 评审通过（candidate → reviewed）**

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 定位记录 | 防改错对象 | 按 ID 找到文件与状态行，向用户复述内容摘要 |
| 2 | 状态变更 | 唯一必须人工的步骤在此完成 | 用户明确说「通过 / 转正」后：`candidate` → `reviewed（YYYY-MM-DD）` |
| 3 | 版本留痕 | 对齐 §2.4 口径 | 单条修正记 PATCH：VERSION / CHANGELOG / CHANGELOG-PLAIN 各补一行 |
| 4 | 提交 | 入库留痕 | commit（`knowledge: 评审通过 <ID>…（vX.Y.Z）`）；push 前确认 |

**② 回流提名（路由 K3）**：按 `knowledge/scenarios.md` K3 原流程执行（核实跨 ≥2 项目实证 → 起草 `_proposals/TEMPLATE-UPGRADE-*.md` → 本仓状态标注 → 提交母模板收件箱）。本技能只做入口识别，不重复 K3 步骤。

## 6. 操作三：核验链接（场景 K5）

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 定核验范围 | 优先查最可能过期的 | 读 `sources.md` 按「最后核验」列排序；用户指定范围时以用户为准 |
| 2 | 逐个访问 | 确认可达 + 页面性质未变（如产品页没变成营销页） | WebFetch / HTTP 状态逐一检查，记录结果 |
| 3 | 回写核验列 | 保持登记表可信 | 可达 → 刷新「最后核验」日期；**不可达 → 不自动改状态**，输出失效清单待人工决策（换链接 / 降级 / 归档） |
| 4 | 确认与留痕 | 写入前确认（rules-core §2） | 回写前列出全部将变更的行等确认；批量核验记 PATCH |

- 访问失败 ≠ 来源失效（可能是网络 / 临时 403）；连续两判才建议人工复核，不单次定死。

## 7. 写入边界（硬约束）

- 操作一纯只读，不落盘、不建文件。
- 操作二 / 三的所有写动作：先列变更清单（文件 + 行 + 前后值）→ 用户确认 → 执行。
- 全程零新增依赖、零脚本；`.claude/skills/kb-ops/` 目录内不放脚本。
- 版本语义：单条评审 / 单条核验记 PATCH；批量核验也记 PATCH（不改知识模型，永不因本技能升 MINOR/MAJOR）。
