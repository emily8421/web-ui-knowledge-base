# 项目特有场景手册（web-ui-knowledge-base）

> **定位**：本项目专属的场景剧本，记录母模板 `template-docs/scenario-guides.md`（A0–A28 / C1–C8）不覆盖的领域特有操作。母模板文件在同步清单内会被下行同步覆盖，**项目特有场景一律写本文件**，不写母模板 scenario-guides。
> **编号空间**：`K1`、`K2`…（K = Knowledge），与母模板 A/C/M 编号空间隔离，避免同步对齐时冲突。
> **格式**：沿用母模板场景条目结构（说明 / 触发 / cwd·前置 / 三层步骤表 / 完成判据 / 下一步 / cmd 指针），保证 AI 消费方式一致。

## 场景速查

| 场景 | 触发说法 | 一句话 |
|---|---|---|
| K1 收集一个设计参考 | 「我想收集 XX」「这个设计很好，收进知识库」 | 按 SOP 五步把一个来源 + 观察收进 `knowledge/` |
| K2 上游语料同步 | 「同步 awesome-design-md」「上游更新了」 | pull 上游 → diff 新增 → 选择性更新镜像与观察 |
| K3 知识晋升提名 | 「这条模式想提名进母模板」 | reviewed + 跨 ≥2 项目实证的模式起草回流提案 |

## K1 收集一个设计参考

- **说明**：看到好设计想收集——按 `knowledge/SOP-collect.md` 五步把来源与观察收进知识库，保证可追溯、许可干净、分级明确。
- **触发**：「我想收集 XX」「ima 的设计很好，收一下」「这个网站不错，进知识库」
- **cwd·前置**：在本项目（web-ui-knowledge-base）

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 先定性来源类型 | 类型决定证据上限与保存策略，闭源产品只能存链接+自有摘要 | 判断：规范(A)/设计系统(B)/研究(B)/产品案例(C)/代码仓(C)/视觉合集(D)；对照 `knowledge/sources.md` 已有登记去重 |
| 2 | 登记 Source | 先占 ID 坑，链接核验状态独立记录 | `sources.md` 加一行（前缀 `SRC-A11Y/DS/HAI/VIS/RES/PROD/CODE-*`）；生命周期默认 candidate |
| 3 | 许可核验 | 决定能存什么：文本语料镜像 or 只链接 | 访问来源 URL 记录「最后核验」；查仓级 LICENSE；**截图/设计稿/字体/图标/品牌资产无论什么许可都不镜像**（永久禁区） |
| 4 | 抽取观察 | 这是唯一需要动脑的步骤：结构化记录看到了什么、什么值得借鉴、什么明确不借鉴 | 产出 `cases/CASE-<产品>-<主题>.md`：配方观察（标「观察到的界面表现」）+ **排除记录**（防机械套用的关键）+ 待复核标注（原料是二次材料时必标）；模式类观察进 `patterns-*.md` / `principles.md` |
| 5 | 分级 | 单一案例就是 D；多案例一致的套路才可立 C 级模式（案例与套路分开记） | Case 整条定 D（产品案例来源上限 C，单例仍 D）；升级通道：观察与既有案例一致时记「候选模式提名」 |
| 6 | 人工评审（第 5 步 SOP 的评审） | 唯一必须人工的步骤：观察是否属实、等级是否恰当、边界是否清楚 | 用户过目后 candidate → `reviewed（日期）` |
| 7 | 提交 | 入库留痕 + CI 校验 | commit（`knowledge: 收集 XX 案例…`）→ push → 看 Project Check 绿 |

- **完成判据**：`sources.md` 有登记行（含链接核验状态）· Case 文件有观察 + 排除记录 · 用户已评审（或明确留 candidate 待评）· commit 已 push 且 CI 绿
- **下一步**：日常继续收集（K1 循环）/ 上游有更新走 K2 / 模式成熟走 K3
- **cmd 指针**：`knowledge/SOP-collect.md`（权威 SOP）；本场景是其「单来源收集」的执行剧本

### K1 实例参考

2026-08-16 收集 ima（commit `7d0c3f3`）：闭源产品定性 → `SRC-PROD-001` 登记 + 链接核验（ima.qq.com 可访问）→ 原料取 LUMEN 仓 `docs/inputs/ima前端交互设计需求说明.md`（二次材料，已标「未经实际产品逐屏复核」）→ Case 落 6 项配方 + 2 项排除 + 6 项待复核 + 1 项候选模式提名（常驻域限定问答面板，待第 2 观察来源）。

## K2 上游语料同步

- **说明**：awesome-design-md 等聚合仓上游更新后，把镜像与观察对齐。
- **触发**：「同步 awesome-design-md」「上游有新案例了」「语料更新」
- **cwd·前置**：在本项目 · 本地有上游克隆（当前 `D:\2-Project\designUI\awesome-design-md`；机器私有路径不入库，交接时口头补）

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 拉上游 | 拿最新语料 | `git -C <上游克隆> pull` |
| 2 | 找差异 | 只处理新增，不重复分析 | diff `knowledge/corpora/awesome-design-md/design-md/` 与上游 `design-md/` |
| 3 | 更新镜像 | 保持语料完整 + 快照可追溯 | 复制新增/变更 DESIGN.md；更新 `corpora/awesome-design-md/SOURCE.md` 快照字段（上游 commit + 日期） |
| 4 | 挑值得分析的 | 上游更新不自动触发抽取 | 人工挑与新主题相关的案例 → 走 K1 步骤 4–6 |
| 5 | 查许可变化 | 许可收紧需降级保存策略 | 核对上游 LICENSE 未变；变了则更新 SOURCE.md + sources.md 保存策略列 |

- **完成判据**：镜像与上游快照一致 · SOURCE.md 快照字段已刷新 · 新案例已决定分析或跳过
- **下一步**：K1（分析新案例）
- **cmd 指针**：`knowledge/SOP-collect.md` §2

## K3 知识晋升提名

- **说明**：本仓 reviewed 且跨 ≥2 项目实证的模式，提名回流母模板核心层。
- **触发**：「这条模式想进母模板」「PAT-VIS-101 验证得差不多了」「晋升核心层」
- **cwd·前置**：在本项目 · 目标模式状态 reviewed · 有 ≥2 项目实证记录（如 LUMEN 试点报告）

| # | 做什么 | 为什么 | 机器执行 |
|---|---|---|---|
| 1 | 核实证据 | core 晋升门槛是跨项目实证，不是收集量 | 收集各项目 RA / 评估报告中的引用与采纳记录 |
| 2 | 起草提案 | 回流走母模板正式流程，不在本仓直接改核心层 | `_proposals/TEMPLATE-UPGRADE-<主题>.md`（去项目化表述 + 证据清单） |
| 3 | 标注状态 | 避免重复提名 | 本仓对应模式状态追加「已提名回流母模板（提案路径）」 |
| 4 | 提交到母模板 | 母模板 `_proposals/` 收件箱是正式入口 | 回母模板仓提交（流程见其 `ai/commands/submit-proposal.md`） |

- **完成判据**：提案已入母模板收件箱 · 本仓状态已标注
- **下一步**：等母模板维护者 triage（C1 场景）
- **cmd 指针**：`ai/commands/submit-proposal.md`（母模板）

## 维护

- 新增场景：追加 `K<n+1>`，不插入小数编号（沿用母模板 §5.1 编号纪律）。
- 场景变化：原位修订步骤表，不改编号。
- 母模板若未来提供「项目特有场景手册」正式机制（见 project-rules §4 挂账），本文件按其规范迁移，编号保留。
